# acceptance

## 完成条件
- SwiftUI前提のiPadモックとして、主要画面の情報構造と遷移意図が一貫している。
- 画面間で用語・状態定義・日時表記ルールが統一されている。
- デモ時に説明する業務シナリオ（確認→判断→更新）が画面遷移で再現できる。
- モックとして視認可能な粒度で、一覧・詳細・更新・例外の最低構成が揃っている。

## UI/UX観点の合格条件
- 主要画面で利用者が次操作を迷わない情報配置になっている。
- 状態の重要度が視覚的に判別でき、色以外の手段（ラベル等）でも認識できる。
- iPadでの横向き閲覧時に、文字可読性とタップ操作性が確保されている。
- 例外状態を含む各画面で、利用者が「何が不足しているか」を理解できる。

## 状態の必須要件
- **空状態**：未登録時に、未登録項目と次に取るべき行動を示す。
- **ローディング状態**：取得中であることと、操作可否を明確にする。
- **エラー状態**：失敗理由の種別（通信・入力・権限）を区別して表示する。
- **完了状態**：更新完了時に反映対象と更新時刻を確認できる。
- **差戻し/保留状態**：理由・依頼者・期限を同時に確認できる。

## デモとして成立する条件
- 営業担当が5〜10分で主要シナリオを途切れず説明できる。
- 顧客が自社運用への置き換えを想像できる具体語（担当、拠点、状態）で構成されている。
- 見栄えより業務判断のしやすさが優先されていることが画面全体から伝わる。
- 「AI生成の試作」ではなく「導入検討可能な業務UI案」として受け止められる。
