# Codex Workflow

## Purpose
この文書は、Codexがこのリポジトリを継続的に扱う際の標準的な進め方を定義します。目的は、作業速度を保ちながらも、100本ノック的な場当たり的増築へ戻らないようにすることです。

## Daily Usage Pattern
日常的な使い方の基本:

1. `README.md` と `AGENTS.md` を読む
2. 関連する `docs/architecture/` と `docs/operations/` を確認する
3. 変更が小修正・設計変更・新機能のどれか分類する
4. 実装より前に、更新すべき文書を洗い出す
5. 差分作成後、関連文書も合わせて更新する

## Flow for Small Fixes
小修正時の流れ:

- 影響範囲を限定する
- リネームや構造変更を混ぜない
- 関連ドキュメントに影響があるか確認する
- 再発防止に文書追記が必要なら行う

小修正でも、運用ルールや責務境界に触れるなら設計変更扱いに格上げします。

## Flow for Design Changes
設計変更時の流れ:

1. 現状の課題を文章化する
2. 変更目的と非目的を分ける
3. 対応するarchitecture文書を更新する
4. 必要なら `docs/decisions/` に判断メモを追加する
5. その後に実装へ着手する
6. 変更後の責務分離が文書通りか確認する

## Flow for New Features
新機能追加時の流れ:

1. その機能が単発実験か、本流候補か判断する
2. 置き場所を責務基準で決める
3. 共通化すべき点と固有実装を分ける
4. 必要なら vision / roadmap にも反映する
5. 実装後、READMEやrepository mapの導線を更新する

## Cases Where Docs Should Come First
以下のケースではドキュメント先行で進めるべきです。

- 新しいディレクトリ責務を導入する時
- アプリ/サービスの境界を変える時
- 共有基盤化を始める時
- 複数エージェント連携のルールを変える時
- 外部提示前に説明線を整える時

## Cases Where Refactoring Should Come First
以下のケースでは、先にリファクタリング計画を切るべきです。

- 同一責務の重複が明確な時
- 命名や配置の揺れで保守が困難な時
- 実験コードが本流コードに混ざっている時
- 将来の共通化対象が散在している時

ただし、リファクタ先行でも文書更新は省略しません。

## Rules to Avoid Falling Back Into “100 Iterations” Mode
- 新規追加の前に、どこへ置くべきかを書く
- 速さだけを理由に責務境界を壊さない
- 未確定事項は明記し、無理に閉じない
- その場しのぎの共通化をしない
- 変更理由を残さないまま構造をいじらない
- 「まず作る」ではなく「何として残すか」を考える

## Review Checklist for Codex
- この変更はどの文書に影響するか把握したか
- 今回の差分は将来の再利用性を上げているか
- 実験と本流を混同していないか
- 不明点を断定していないか
- 次の人/AIが見ても意図を追えるか
