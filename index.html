About / Portfolio Intro

本ページは、AI活用の利便性とセキュリティ運用の両立を示すためのポートフォリオです。Codex 5.4 を制作パートナーとして活用しつつ、情報の持ち出し・権限の与えすぎ・APIキー管理・未検証スキル導入といったリスクを常に点検する設計を採っています。

私は高機密環境の完全閉域運用を断言する立場ではありませんが、日常開発では情報分類・権限制御・秘密情報の保管方法を重視しています。原則は、 「便利さより先に、失って困るものを渡さない」 です。

Security Mindset

情報分類

公開・社外秘・機密を分け、AIへ渡す情報を事前に仕分けます。

権限制御

実行権限・アクセス範囲を最小化し、不要な自動実行を避けます。

機密の分離

コードと秘密情報を同居させず、保管場所を分離します。

ログと監査

送信内容と設定変更を追跡可能にし、説明責任を担保します。

供給網への警戒

Skill/Plugin/拡張機能の出所と更新履歴を確認して導入します。

# AIエディタ利用

## セキュリティガイドライン

ここから、実務で運用しやすい形に落とし込んだ本編です。

5 Principles

1. 失って困るものを渡してはいけない

要約: 取り返しがつかない情報は入力しない。

危険: 学習・ログ保持・漏えい時の被害が大きい。

対策: マスキング、ダミー化、送信前レビューを徹底。

2. 営業秘密を渡してはいけない

要約: 競争優位に関わる知見は社外AIへ渡さない。

危険: 守秘義務違反や契約違反に発展する。

対策: 機密区分ラベルを付与し、送信禁止ルールを明文化。

3. クローフィッシング脅威を軽視しない

要約: 組織内OpenClawを狙う誘導攻撃を前提に設計する。

危険: 認証情報・内部文書の窃取に直結する。

対策: 検証済み接続先のみ許可、URL検証・多要素認証を徹底。

4. APIキー等をJSON保存させない

要約: 機密を平文ファイル化しない。

危険: Git誤コミットや共有時に漏えいする。

対策: Secret Manager / .env分離 / ローテーション運用。

5. スキルをむやみに追加してはいけない

要約: 便利な拡張ほど、権限と供給網リスクを確認する。

危険: 過剰権限・悪性アップデートの入口になる。

対策: 検証環境で試験、署名確認、最小導入を維持。

Information Classification

情報種別 AI入力可否 補足
公開情報可出典確認のうえ利用
OSSコード可ライセンス表記を維持
社内コード制限付き匿名化・差分限定で扱う
未公開設計原則禁止社内承認がある場合のみ
顧客情報禁止契約・法令に基づき遮断
個人情報禁止特定可能情報は送信しない
認証情報禁止キー/トークンは専用保管

Tool Usage Policy

  • 本番フォルダをそのままAIへ読ませない
  • .env / 秘密鍵 / 証明書をプロジェクト分離する
  • 承認なしで自動実行させない
  • Skill / Pluginは検証後に限定導入する
  • ログを残し、設定変更はレビューフローに乗せる

Security Maturity

  2. L2 小規模開発
  3. L3 組織利用
  4. L4 機密開発
  5. L5 完全閉域

私の現在地は日常開発〜小規模組織利用（L2〜L3）を強く意識する段階です。将来的には、より高い成熟度に対応できる運用設計へ段階的に拡張する方針です。
